\section{\iic{} recap}
\label{sec:bg-i2c}

The Inter-Integrated Circuit (\iic{}) bus is a two-wire, multi-drop serial interconnect
comprising a serial clock line (SCL) and a serial data line (SDA). Both lines are
\emph{open-drain} (OD): every device can only pull a line Low, and a passive pull-up
resistor returns it High, so the bus behaves as a wired-AND of all attached drivers.
A transfer is framed between a START condition (SDA driven Low while SCL is High) and a
STOP condition (SDA released High while SCL is High). After START the controller shifts
out a 9-bit address byte --- a 7-bit target address followed by a read/not-write (RnW)
bit, most-significant bit first --- and the addressed target answers with an
acknowledge (ACK) by pulling SDA Low during the ninth clock; an unanswered byte reads
back as a not-acknowledge (NACK). Data then flows in 8-bit bytes, each followed by an
ACK/NACK, until a STOP closes the frame. A target that cannot keep pace may hold SCL Low
(clock stretching) to stall the controller.

Three properties of this model limit \iic{} as device counts and data rates rise, and I3C
is designed to remove them: the open-drain pull-ups cap the practical clock rate and waste
static power; addresses are fixed at manufacture, so two parts that share an address
cannot coexist on one bus; and the bus has no native interrupt, forcing the controller to
poll. These limitations motivate the push-pull signalling, dynamic addressing, and
in-band interrupts introduced next.

\section{MIPI I3C Basic v1.1.1 (SDR, frame format)}
\label{sec:bg-i3c-sdr}

I3C (Improved Inter-Integrated Circuit) preserves the two-wire SCL/SDA topology and the
START/STOP framing of \iic{}, but adds a \SI{1.8}{\volt} LV-CMOS \emph{push-pull} (PP)
data phase that actively drives the bus in both directions, raising the Single Data Rate
(SDR) clock ceiling to \SI{12.5}{\mega\hertz}~\cite{mipi_i3c_basic}. The address and
arbitration phases remain open-drain for backward compatibility (\cref{sec:bg-odpp});
only the data phase switches to push-pull.

I3C reserves the broadcast address \texttt{7'h7E}, which the controller uses both to mark
the start of native I3C activity on a mixed bus and to carry Common Command Codes
(\cref{sec:bg-ccc}). Two SDR frame shapes carry private data between the controller and a
target. In an \textbf{SDR private write}, the controller issues a START (optionally
preceded by the \texttt{7E} broadcast header), addresses the target with RnW${=}0$, and
then transmits data bytes in the push-pull phase; each byte is followed by a
\emph{Transition Bit} (T-Bit) whose value is the \emph{odd parity} of the byte, letting
the target detect a corrupted byte. In an \textbf{SDR private read}, the controller
addresses the target with RnW${=}1$ and the target drives the data bytes; here the T-Bit
carries \emph{end-of-data} signalling rather than parity --- the target holds it High
while more bytes follow and drives it Low on the final byte, after which the controller
issues a STOP or Repeated START. This dual role of the T-Bit (parity on writes,
end-of-data on reads), summarised in \cref{fig:sdr-frames}, is central to the bus-level
serialisers described in \cref{ch:architecture-rtl}.

\section{Bus conditions (START / Repeated START / STOP)}
\label{sec:bg-bus-conditions}

Three edge conditions delimit and chain transfers. A \textbf{START} (S) is an SDA
falling edge while SCL is High; a \textbf{STOP} (P) is an SDA rising edge while SCL is
High; and a \textbf{Repeated START} (Sr) is a START issued without an intervening STOP,
used to chain phases --- for example to switch from the open-drain broadcast header to the
push-pull data phase, or to turn the bus around between a write and a read.

The MIPI specification further defines three \emph{distinct} idle conditions that this
thesis is careful not to conflate~\cite{mipi_i3c_basic}. This controller uses only the
\textbf{Bus Free Condition} (\S5.1.3.2.1) --- the interval after a STOP and before the next
START, sustained for at least $t_{\mathrm{CAS}}$ --- which it detects before initiating a
transfer. The longer \textbf{Bus Available} (\S5.1.3.2.2) and \textbf{Bus Idle}
(\S5.1.3.2.3) conditions are not used, because the events that need them (target-initiated
START, Hot-Join) are out of scope. The bus monitor and SCL generator that realise these
conditions are detailed in \cref{ch:architecture-rtl}.

\section{Open-drain versus push-pull signalling}
\label{sec:bg-odpp}

I3C uses two electrical signalling modes on the same wires and switches between them within
a single transfer. The \textbf{acknowledge bits and the arbitrated address phases stay
open-drain}: the bus is released to be pulled High and any device may pull it Low, which
preserves \iic{}-style wired-AND arbitration, lets legacy \iic{} targets participate, and
makes the bit-by-bit ENTDAA arbitration of \cref{sec:bg-entdaa} possible. Once the
controller has won the bus, the \textbf{data phase --- and any address it drives after a
Repeated START --- switch to push-pull}, where the active driver sources and sinks current
directly; this removes the RC time constant of the pull-up and is what permits the
\SI{12.5}{\mega\hertz} SDR rate.

The boundary is crossed at a Repeated START, where the controller turns the bus from the
open-drain \texttt{0x7E} header to push-pull for the address and data that follow, while the
ACK/NACK bits remain open-drain (\cref{fig:sdr-frames}). The RTL realisation of this mode
select and its switching behaviour are described in \cref{ch:architecture-rtl}.

\section{Dynamic Address Assignment via ENTDAA}
\label{sec:bg-entdaa}

I3C replaces \iic{}'s fixed addressing with run-time Dynamic Address Assignment (DAA),
which eliminates address collisions and supports devices that share a part number. This
design implements DAA through the ENTDAA (Enter Dynamic Address Assignment) procedure from
the controller's perspective. The controller issues a START followed by the broadcast
address \texttt{7'h7E}${+}$W and the ENTDAA Common Command Code (\texttt{0x07}); it then
enters a loop, issuing a Repeated START and \texttt{7'h7E}${+}$R for each round. Every
not-yet-addressed target answers by streaming its unique 64-bit identity ---
a 48-bit Provisioned ID (PID), an 8-bit Bus Characteristics Register (BCR), and an 8-bit
Device Characteristics Register (DCR) --- most-significant bit first, with no ACK between
fields.

Because the identity stream is open-drain and wired-AND, it doubles as an arbitration
mechanism: when several targets respond at once, a target that drives a logic~1 but reads
back a~0 on SDA has lost to a lower-valued identity and withdraws, so exactly one target
wins each round. The controller then sends that winner a 7-bit dynamic address plus a
parity bit, the target ACKs, and the loop repeats until a round goes unanswered, at which
point a STOP closes the procedure. The assigned addresses are recorded in a 32-entry
Device Address Table (DAT). \Cref{ch:architecture-rtl} realises this as a two-FSM
subsystem --- a loop manager and a per-round arbitration FSM.

\section{Common Command Codes (CCC) overview}
\label{sec:bg-ccc}

Common Command Codes (CCCs) are standardised commands the controller issues after the
\texttt{7'h7E} broadcast header to configure and manage targets. They come in two framings.
A \textbf{Broadcast CCC} is addressed to all targets at once
(\texttt{[S]} \texttt{[7E+W]} \texttt{[CCC]} \dots\ \texttt{[P]}); a \textbf{Direct CCC}
targets one device by following the code with a Repeated START and that device's address
(\texttt{[S]} \texttt{[7E+W]} \texttt{[CCC]} \texttt{[Sr]} \texttt{[addr+RnW]} \dots\
\texttt{[P]}).

Of the full CCC catalogue, this design implements only the essential subset needed to
bring up and manage an SDR bus, summarised in \cref{tab:ccc-supported}. ENTDAA
(\texttt{0x07}, broadcast) drives dynamic address assignment; ENEC (\texttt{0x00}
broadcast / \texttt{0x80} direct) and DISEC (\texttt{0x01} broadcast / \texttt{0x81}
direct) enable and disable target-generated events. All other CCCs are out of scope
(\cref{sec:req-oos}).

\section{UVM 1.2 methodology overview}

The design is verified with Universal Verification Methodology (UVM) 1.2, a standardised
SystemVerilog class library for reusable, layered verification environments~\cite{uvm12}.
A UVM test selects a scenario, sequences generate transaction items, and agents translate
those items into interface activity while monitors reconstruct observed transactions.
Transaction-Level Modelling (TLM) analysis ports distribute observations to scoreboards
and coverage collectors without tightly coupling the components. This vocabulary is the
background needed for the verification requirements below; the project-specific topology,
agents, scoreboard connections, configuration, and execution flow are owned by
\cref{ch:verif-method} and are not repeated here.

\section{Performance targets}
\label{sec:req-performance}

The controller targets an SDR push-pull SCL of up to \SI{12.5}{\mega\hertz} and a legacy
\iic{} Fast-Mode SCL of \SI{400}{\kilo\hertz}, both kept within the MIPI I3C Basic Table~87
and \iic{} Fast-Mode limits (SDR $t_{\mathrm{LOW}}, t_{\mathrm{HIGH}} \ge \SI{24}{\nano\second}$,
$t_{\mathrm{SU,DAT}} \ge \SI{3}{\nano\second}$, $t_{\mathrm{SCO}} \le \SI{12}{\nano\second}$).
Because SCL is generated by counting system-clock cycles, the design runs in a single clock
domain at a minimum of \SI{333}{\mega\hertz} (a \SI{3}{\nano\second} period; the testbench
clocks the DUT at exactly this rate). This rate is set by the target clock-to-data-out budget:
$t_{\mathrm{SCO,max}} = 4 \times T_{\mathrm{sys}} = 4 \times \SI{3}{\nano\second} =
\SI{12}{\nano\second}$, which meets the \SI{12}{\nano\second} specification maximum.

SCL timing is not hard-wired but is programmable through control/status registers (CSRs);
the SCL Low and High phases are loaded from per-mode count registers, so software can
retune the bus without RTL changes. \Cref{tab:perf-targets} lists the reset-default counts
taken directly from the RTL register file. Separate Low-period counts exist for the
push-pull data phase and the slower open-drain address phase
($t_{\mathrm{LOW,OD}}$), and a separate set of counts governs \iic{} Fast-Mode. The
defaults are chosen to sit within the spec ceilings with margin; the achieved frequency
follows from the loaded counts and the system-clock period.

\section{Software-visible interface (32-bit register bus)}
\label{sec:req-swif}

The controller is exposed to host software through a deliberately simple 32-bit register
interface --- not AXI4 or AHB-Lite as in the reference design --- chosen to keep the focus
on protocol behaviour rather than bus-adapter logic. A write presents an address, write
data, and a write-enable in one cycle (\texttt{reg_addr_i[11:0]} ${+}$
\texttt{reg_wdata_i[31:0]} ${+}$ \texttt{reg_wen_i}); a read presents an address and a
read-enable and receives data with a ready handshake (\texttt{reg_addr_i[11:0]} ${+}$
\texttt{reg_ren_i} $\rightarrow$ \texttt{reg_rdata_o[31:0]} ${+}$ \texttt{reg_ready_o}).

Above this register contract sit the transaction-staging structures: a command is staged
as a two-DWORD command descriptor before being pushed into the command queue; write
payload is written through a TX data-buffer window and read payload is retrieved through an
RX data-buffer window; and each completed command produces a response descriptor in the
response queue. The full register map and descriptor layouts are deferred to the
appendices and detailed in \cref{ch:architecture-rtl}.

\section{Verification requirements}
\label{sec:req-verification}

Verification is considered closed when: every directed virtual sequence in its functional
category passes; the scoreboard's cross-checks of command, response, receive-data, CSR, and
DAT state are clean; the SystemVerilog Assertions (SVA) bound into the testbench remain
silent; and the categorised regression targets run green. A key part of this contract is that
the scoreboard checks the controller against \emph{exactly} the set of response error-status
codes the design is required to generate --- no more and no less. That \texttt{ERR\_STATUS}
encoding, with the codes this SDR-only design actually emits marked as generated, is presented
alongside the command FSM that produces it in \cref{ch:architecture-rtl}
(\cref{tab:err-status}); the HDR-only codes (\texttt{Crc}, \texttt{Parity}, \texttt{Frame})
are declared for interface compatibility but never produced. One distinction is part of the
verification contract because its two codes are easy to swap: \texttt{Nack} (\texttt{0x5}) is
reserved for the ENTDAA path where a dynamic address is rejected twice (retry exhausted),
\emph{not} for a data NACK, whereas a data-phase NACK or a bus abort returns
\texttt{I2cDataNackOrI3cBusAborted} (\texttt{0x9}).
